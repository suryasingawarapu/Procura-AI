§ 03 · PERSISTENT MEMORY

Memory that outlives the conversation

Each agent owns a memory space in Postgres (Supabase with pgvector). Writes are atomic and versioned, every change carries its provenance, and nothing is ever overwritten in place.

01

Scoped per agent

An agent's identity is bound in code, never passed by the model, so Vendra cannot read or write Finora's memory.

02

Atomic versioning

Identical content is a no-op. Changed content supersedes the active version and creates the next one in a single transaction.

03

Provenance graph

supersedes and derived_from edges record where every fact came from, with ancestry and descendant queries.

04

Policy-controlled sharing

Who may share with whom lives in the database. A pair that isn't listed is denied, and shared copies are new rows with lineage.

05

Vector search

Memories can carry an embedding and be searched by similarity (pgvector), limited to the agent's own active memories. Embeddings are generated when an embedding provider is configured.

06

Stale detection & document expiry

Superseded, archived and expired memories are left out of an agent's context. A supplier's verdict carries the expiry of the first document behind it, so it goes stale by itself when a GST certificate lapses. A shared copy goes stale when its source, or any ancestor along the sharing path, changes.

07

Summary-first retrieval

Long histories are folded into a summary that records exactly what it covers. Procura reads the summary of an item's quotation history first, then opens the supporting records to see what changed. If something the summary covers changes, it is marked stale and rebuilt, never used.

08

Conflict detection & resolution

Every quotation is a claim with its source and document date. When an email says ₹50,000 and an updated PDF says ₹53,000, the more authoritative, newer source wins automatically; when that cannot be decided, the task waits and you choose in the chat. The loser is kept, marked disputed.

09

Agents that use the shared memory

The coordinator relays Vendra's verdicts to Procura, which selects suppliers from what it received; Finora refuses to proceed if the evidence it holds is no longer current. Every hand-off is recorded as data.

§ 07 · QUESTIONS

Frequently asked

Is the chat actually calling real agents, or is it scripted?

Every reply is a real API call. Vendor eligibility, quotation ranking and budget checks are deterministic code — never an LLM guess — and the LLM is used only to route your message and narrate the result in plain language.

What's the difference between demo and live mode?

Demo mode runs against a fully isolated synthetic vendor pool and never touches production storage. Live mode talks to a real ERPNext instance and, if configured, can submit a real Purchase Order — it's always visibly flagged in the chat header.

What happens if my request is missing information?

The agent asks for exactly what's missing (e.g. an item code) and resumes the same task once you reply — nothing is restarted or lost.

What happens to a task if I close the browser or the server restarts?

Nothing is lost. The task lives in persistent memory, not in the browser or the process. A follow-up message later recalls the active version from the database and continues from the state it was in.

Is my conversation stored?

In live mode, yes: each chat turn is stored in persistent memory and periodically summarized, so a long conversation is compressed instead of cut off and survives a restart. Deleting a conversation in the sidebar deletes it from the database too. Demo mode stores nothing.

Who can approve a purchase?

Approval authority is checked against a real role-based limit policy and the agent pipeline's actual recommended cost — never a stale original estimate.
